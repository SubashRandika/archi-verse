## Learning objectives

After this module, the learner can:

1. Explain why one general-purpose API serves different front ends badly: too many round trips
   on mobile, and too much or too little data for each screen.
2. Describe a Backend for Frontend: a small server-side layer built for one front end, owned
   by the team that builds that front end.
3. Explain aggregation (one call in, several calls out in parallel) and why the slowest call
   sets the pace.
4. Shape a response for a screen, and keep working with partial data when one service is
   slow.
5. Weigh the costs (duplicated logic, one more service to run) and compare a BFF with an API
   gateway and with GraphQL.

## The running example

The shop has a web site and a mobile app. Both show the **Order details** screen for order
1042: the order and its items (from the **Orders service**), the delivery address (from the
**Users service**) and "You may also like" products (from the **Recommendations service**).

- The **web** page shows everything: all items with photos, the full address, 12 suggestions.
- The **mobile** screen is small: item names and totals, the city only, 3 suggestions.
- The mobile app is on a mobile network: about **300 ms** for every round trip (Review 4).
  The web is on fast Wi-Fi: about **40 ms**.

Today each service has one general-purpose REST API, and both apps call all three themselves.

## Chapter 1: One API for everyone

### Step 1. One API for everyone

**Scene:** the web browser calls Orders, Users and Recommendations directly, one after
another, and gets three answers. Badge on the browser: "3 calls · 120 ms".

#### Beginner

> To show one order, the web page needs three things: the order, where to deliver it, and
> some ideas for what else you might like. Each thing lives in a different service, so the
> page asks all three, one after the other. On fast Wi-Fi that's quick.
>
> **Like in real life:** to make dinner you walk to the butcher, then the baker, then the
> greengrocer. If they are all on your street, it doesn't take long.

#### Advanced

> Each service exposes a general-purpose REST API designed around its own data, not around any
> screen. The client composes the screen itself: `GET /orders/1042`, then
> `GET /users/u_7f3a/address`, then `GET /recommendations?for=1042`. Calls that depend on an
> earlier answer (the user id comes with the order) must run one after another.
>
> **Example:** three round trips on Wi-Fi.
>
> ```text
> GET /orders/1042                 40 ms
> GET /users/u_7f3a/address        40 ms   (needs userId from the order)
> GET /recommendations?for=1042    40 ms
> total                           120 ms
> ```

**Terms:** General-purpose API · Round trip · Client-side composition

---

### Step 2. The chatty mobile app

**Scene:** the mobile app makes the same three calls, much more slowly; each round trip takes
visibly longer. Badge on the phone: "3 calls · 900 ms".

#### Beginner

> The phone does exactly the same, but its connection is slow, like shouting across a big
> field. Every question takes a long time to arrive and a long time to come back. Three
> questions take three long waits.
>
> **Like in real life:** the butcher, the baker and the greengrocer are now in three different
> villages. Each trip takes ages, and you need three trips.

#### Advanced

> On a mobile network latency, not bandwidth, dominates: each round trip costs hundreds of
> milliseconds, and requests over a fresh connection pay for DNS, TCP and TLS too. A screen
> that needs N sequential calls costs N round trips. It also costs battery: the radio stays
> awake for each request.
>
> **Example:** the same three calls on a mobile network.
>
> ```text
> GET /orders/1042                300 ms
> GET /users/u_7f3a/address       300 ms
> GET /recommendations?for=1042   300 ms
> total                           900 ms   (plus any connection setup)
> ```

**Terms:** Latency · Chatty API

### Step 3. Too much, too little

**Scene:** the three answers to the phone are big: a badge shows "38 KB received, 4 KB used".
The web browser's badge shows "1 more call needed" (it wants delivery estimates the API
doesn't give).

#### Beginner

> The services send the same big answer to everyone. The phone gets photos and details it
> will never show, and has to throw most of it away. And sometimes the web page wants
> something the answer doesn't have, so it must ask again.
>
> **Like in real life:** you ask for one apple and get a whole crate. Your friend asked for
> apples **and** the price, but the crate has no price tag, so they have to go back.

#### Advanced

> A general-purpose API returns one shape for everyone, so some clients **over-fetch** (data
> they discard: wasted bytes, parsing time and memory on a phone) and others **under-fetch**
> (they need another call for a missing field). Adding fields for one client grows the
> payload for all of them; removing fields breaks someone. The API's design ends up
> negotiated between teams with different needs.
>
> **Example:** what the phone receives and what it shows.
>
> ```text
> /orders/1042            21 KB   (items with photos, prices, tax lines, history)
> /users/…/address         3 KB   (full address, phone numbers, preferences)
> /recommendations        14 KB   (12 products with images)
> received                38 KB   used ≈ 4 KB
> ```

**Terms:** Over-fetching · Under-fetching

## Chapter 2: A backend per front end

### Step 4. Meet the BFFs

**Scene:** the direct connections disappear. The Web BFF and Mobile BFF light up; the web
browser now talks only to the Web BFF, the phone only to the Mobile BFF.

#### Beginner

> Now each app gets its own helper on the server. The web page has a web helper, the phone
> has a phone helper. Each helper knows exactly what its app needs, and does the running
> around for it.
>
> **Like in real life:** instead of walking to three shops, you have a personal shopper who
> knows what you like. You ask once, and they bring you one bag.

#### Advanced

> A **Backend for Frontend** is a server-side component built for exactly one user experience:
> one for the web, one for the mobile app (sometimes one per platform, iOS and Android). It
> sits behind the API gateway (which still handles TLS, authentication and rate limits for
> everyone) and in front of the services. It contains no business rules of its own; it
> composes and adapts.
>
> **Example:** the request paths.
>
> ```text
> web     →  gateway  →  web-bff.internal     →  orders, users, recommendations
> mobile  →  gateway  →  mobile-bff.internal  →  orders, users, recommendations
> ```

**Terms:** Backend for Frontend (BFF) · Experience API

---

### Step 5. One call in, three calls out

**Scene:** the phone sends one request to the Mobile BFF. The Mobile BFF sends three requests
at the same time (to Orders, then Users and Recommendations side by side), the three answers
come back, and one answer goes to the phone. Badge on the phone: "1 call · 380 ms".

#### Beginner

> The phone asks its helper just once. The helper, who is close to the services, asks all three
> at the same time, collects the answers and sends back one. The phone waits for only one slow
> trip instead of three.
>
> **Like in real life:** your personal shopper sends three friends to the three shops at the
> same time. You get one bag, and it arrives faster.

#### Advanced

> The BFF **aggregates**: it turns one client request into several service calls inside the
> data centre, where a round trip costs about 1 ms instead of 300. Independent calls run in
> parallel, so the total is roughly the **slowest** call, not the sum. Calls that depend on
> earlier answers still run in sequence (Users needs the userId from the order).
>
> **Example:** where the time goes now.
>
> ```text
> phone → Mobile BFF                       300 ms   (one mobile round trip)
> BFF → orders                              25 ms
> BFF → users ∥ recommendations             55 ms   (in parallel: the slower one counts)
> total                                   ≈ 380 ms   (was 900 ms)
> ```

**Terms:** Aggregation · Fan-out · Parallel calls

---

### Step 6. Each screen gets its own answer

**Scene:** the web browser asks the Web BFF and the phone asks the Mobile BFF, at the same time.
Their answers come back with size badges: "38 KB" to the web, "4 KB" to the phone. Click
either packet to compare the two answers.

#### Beginner

> The two helpers pack different bags. The web helper packs everything the big screen shows:
> photos and twelve ideas. The phone helper packs only what fits on a small screen: names,
> totals and three ideas. Nobody gets things they will throw away.
>
> **Like in real life:** the same shop packs a big family box for one customer and a small
> lunch box for another. Same shop, different boxes.

#### Advanced

> Each BFF shapes the response for its screen: it selects fields, renames them for the UI,
> merges data from several services, formats values (dates, money) for display and decides
> image sizes. The services' APIs stay general; the BFF absorbs the differences.
>
> **Example:** the mobile answer.
>
> ```http
> HTTP/1.1 200 OK
> Content-Type: application/json
> Content-Length: 4113
>
> {"order":{"id":1042,"status":"On its way","total":"LKR 12,400",
>  "items":[{"name":"Desk lamp","qty":1},{"name":"USB-C cable","qty":2}]},
>  "deliverTo":"Colombo",
>  "suggestions":[{"id":88,"name":"Lamp bulb"},{"id":91,"name":"Cable clips"},{"id":17,"name":"Desk mat"}]}
> ```

**Terms:** Response shaping · Payload

---

### Step 7. Owned by the front-end team

**Scene:** the web browser and the Web BFF glow together, then the phone and the Mobile BFF
together: one team each. Badges: "web team", "mobile team".

#### Beginner

> The people who make the web page also make the web helper. When they change the page, they
> can change their helper the same day, without asking anybody else. The phone team does the
> same with theirs.
>
> **Like in real life:** each family has its own shopper, who listens only to them. If you
> want something new in your bag, you tell your shopper, and nobody else has to agree.

#### Advanced

> A BFF is owned by the team that owns the front end, so a screen and its API change and ship
> together, without negotiating with other clients' teams (Conway's law, used on purpose).
>
> A web BFF is also the safest place to keep tokens out of the browser: the BFF holds the
> OAuth tokens on the server and gives the browser only an `HttpOnly`, `Secure`, `SameSite`
> session cookie, so a script injected into the page (XSS) cannot steal them (Review 5).
>
> **Example:** what the browser holds with and without a BFF.
>
> ```text
> without BFF:  browser holds  access_token + refresh_token   (readable by any page script)
> with BFF:     browser holds  Set-Cookie: sid=…; HttpOnly; Secure; SameSite=Strict
>               BFF holds      the tokens, and adds Authorization: Bearer … to service calls
> ```

**Terms:** Conway's law · Token handler · HttpOnly cookie

## Chapter 3: Trade-offs

### Step 8. The costs, and the alternatives

**Scene:** both BFFs light up and send the same call to Orders: a badge on each BFF shows
"same rule, 2 copies". Then everything is lit: the whole picture.

#### Beginner

> Two helpers means two things to look after. Sometimes both helpers learn the same trick,
> and later one of them changes it and the other doesn't, so the two apps behave a little
> differently. BFFs are great when the apps really need different things. When they don't,
> one shared helper is simpler.
>
> **Like in real life:** two personal shoppers is nice, but you pay two people, and they
> might each remember your favourite bread differently.

#### Advanced

> Costs: one more deployable per front end (hosting, monitoring, on-call), logic that gets
> copied between BFFs and drifts (move real business rules into the services), and an extra
> hop of latency inside the data centre.
>
> Alternatives and companions:
>
> - **API gateway:** shared concerns for every client (TLS, auth, rate limits). It sits in
>   front of the BFFs; it should not grow screen-specific logic.
> - **GraphQL:** one flexible endpoint where the client asks for exactly the fields it needs;
>   it solves over- and under-fetching without a BFF per client, at the cost of a schema and
>   resolver layer (often federated over the services).
> - **A BFF is worth it** when front ends differ a lot (web vs mobile vs TV) and are built by
>   different teams.
>
> **Example:** who has used it. SoundCloud used BFFs while splitting its monolith (described by
> Phil Calçado), and Sam Newman wrote up the pattern. Netflix ran device-specific adapter
> scripts on its API platform, one per kind of device.

**Terms:** API gateway · GraphQL · Code duplication

## Scenarios

### One service is slow (branches from step 5)

1. **Recommendations slows down.** _Scene:_ Recommendations turns amber ("slow"); the Mobile
   BFF's calls to Orders and Users come back, the one to Recommendations doesn't. The BFF's
   badge counts its budget: "waiting · 200 ms".
   - _Beginner:_ One of the three shops is very slow today. The helper already has two of the
     three things, and waits a little for the third.
   - _Advanced:_ In a fan-out, the slowest dependency sets the response time. Each downstream
     call needs its own timeout inside an overall budget for the request.
2. **Answer with what you have.** _Scene:_ the budget runs out; the BFF answers the phone
   without suggestions (green, badge "partial"); the late answer is dropped.
   - _Beginner:_ The helper doesn't make you wait for ever. You get your order and address now,
     just without the ideas. That part of the screen stays empty.
   - _Advanced:_ The BFF returns a **partial response** for optional data (recommendations are
     nice to have; the order is not), marks what is missing, and lets the UI hide that
     section. Required data failing is still an error. A circuit breaker around each call
     (previous module) stops the BFF waiting on a service that is down.

### A web-only change (branches from step 7)

1. **The web wants a new field.** _Scene:_ the Web BFF works ("deploying"), its badge changes
   to "v2.5"; the Mobile BFF and the services stay as they are.
   - _Beginner:_ The web team wants to show "arrives Thursday". They teach their helper to ask
     for the delivery date. Nobody else has to change anything.
   - _Advanced:_ The web team adds `estimatedDelivery` to its BFF, using a field Orders already
     has. No change to the services' APIs, no coordination with the mobile team, no new
     version of a shared API.
2. **Only the web sees it.** _Scene:_ the browser asks again and gets the new answer; the phone
   asks and gets its usual answer, unchanged.
   - _Beginner:_ The web page shows the delivery day. The phone app works exactly as before.
   - _Advanced:_ Each client's contract changes on its own schedule. The mobile app, which
     ships through app stores and has old versions in use for months, is not affected; when it
     wants the field, the mobile BFF adds it, still serving the old app versions.

## Components

### Web browser (client)

The shop's web site. _Advanced:_ renders the full Order details page; talks only to the Web
BFF (through the gateway); with a BFF, holds a session cookie instead of tokens.

### Mobile app (client, new shape)

- **Purpose:** _Beginner:_ the shop's app on your phone. _Advanced:_ a native app on a slow,
  high-latency network, with old versions in use for months.
- **Talks to:** Mobile BFF. **Limitations:** every round trip is expensive; can't be updated
  instantly (app-store releases).

### Web BFF and Mobile BFF

- **Purpose:** _Beginner:_ a helper on the server for one app, who knows what that app needs.
  _Advanced:_ a server-side layer for one user experience: aggregates service calls, shapes
  responses, may handle sessions and tokens; owned by that front end's team.
- **Responsibilities:** aggregate · shape responses · per-call timeouts and partial answers ·
  (web) keep tokens server-side.
- **Technologies:** Node.js (Express, Fastify, NestJS), Next.js route handlers, Spring Boot,
  Kotlin, Go; sometimes a GraphQL server.
- **Advantages / limitations:** each front end gets exactly what it needs and moves at its own
  pace / one more service per front end; duplicated logic can drift.

### Orders service, Users service, Recommendations service

General-purpose services owning their data: the order and items, users and addresses, product
suggestions. Recommendations is "nice to have" data: a screen works without it.

## Review

1. **No API gateway in the scene.** It sits in front of the BFFs in a real system; step 4 and
   step 8 say so. Leaving it out keeps a seven-part scene readable. _Recommended._
2. **Chapter 1 shows the apps calling the services directly,** on connections that appear only
   in those steps, then disappear when the BFFs arrive. _Recommended:_ it makes the "before"
   visible. The alternative is to explain "before" in text only.
3. **Size badges** ("38 KB", "4 KB") and round-trip badges ("3 calls · 900 ms") to show what
   packets can't. _Recommended._
4. **Illustrative numbers:** 300 ms per mobile round trip, 40 ms on Wi-Fi, about 1 ms inside the
   data centre, 38 KB vs 4 KB. Realistic orders of magnitude, stated as illustrations.
   _Recommended._
5. **The security point in step 7** (a web BFF keeps OAuth tokens out of the browser, the
   "token handler" pattern). It is one of the strongest reasons for a web BFF today, but it
   widens the topic. _Recommended:_ keep it, at the Advanced level only.
