## Learning objectives

After this module, the learner can:

1. Say what idempotent means (repeating an operation has the same **effect** as doing it once),
   which HTTP methods are idempotent by definition (`GET`, `PUT`, `DELETE`) and which are not
   (`POST`, `PATCH`).
2. Name the everyday sources of duplicate requests (double clicks, retries after timeouts, lost
   answers, network switches, redelivered messages) and explain why the server, not the
   client, must make repeats safe.
3. Implement the client side of an idempotency key: one key per operation, kept across retries
   and reloads, replaced when the operation changes.
4. Describe the server side: record the key before doing the work, store the answer with it,
   replay the stored answer for repeats.
5. Handle the hard cases: two requests with one key at once (`409`), one key with a different
   request (`422`), keys that expire, and a crash between the side effect and saving the
   answer, by passing a key on to the next system.

## The running example

The same shop as the Retry module. **Shopper A** pays for order 1042 on a laptop:

```http
POST /payments HTTP/1.1
Host: api.shop.example
Content-Type: application/json
Idempotency-Key: 7f3a9c2e-4b1d-4e8a-9f60-2d5c1b8e3a47

{"orderId":1042,"amount":"12400.00","currency":"LKR"}
```

The **Payments service** records the key in the **Payments DB**, asks the **Card processor**
(an outside company, like a bank or Stripe) to take the money, saves the answer with the key,
and replies `201 Created` with `{"id":"pay_81f2","status":"succeeded"}`.

**Illustrative numbers** (Review 1): keys are kept for **24 hours**; a key that has been "in
progress" for more than **60 seconds** is treated as abandoned (Review 6). Playback compresses
time; badges show the real values. Keys are shortened on badges ("key 7f3a…").

| Shopper A      | client   | Shopper A      | Makes the key, sends the payment, retries                               |
| Payments       | service  | Payments       | Checks the key, does the work once, stores and replays the answer       |
| Payments DB    | database | Payments DB    | Charges and the idempotency-key table, written in one transaction       |
| Card processor | service  | Card processor | An outside system that takes the money; it accepts its own key (step 8) |

Layout: Shopper A → Payments → Card processor along one line; the Payments DB behind Payments,
as in the Retry module. Connections: Shopper A to Payments, Payments to the Payments DB,
Payments to the Card processor. No new shapes.

**Badges** show what packets can't:

- On Shopper A: the key and the attempt ("key 7f3a… · attempt 2"), and outcomes ("paid", "409
  · try again shortly", "422 · key reused").
- On the Payments DB: the key's state ("key 7f3a… · in progress", "… · done · 201 saved") and
  the count that matters ("1 charge · 3 requests", "charged twice").
- On Payments: what it did with a repeat ("replayed", "different body").
- On the Card processor: its own count ("charged once", "charged once · replayed").

## Chapter 1: Safe to repeat?

### Step 1. Same request, twice

**Scene:** Shopper A changes the delivery address: `PUT /orders/1042/address` is sent twice;
both succeed and the Payments DB badge reads "address: 12 Lake Rd · same". Then Shopper A sends
`POST /payments` twice, **without a key**; both succeed and the badge reads "charged twice".

#### Beginner

> Some things are fine to do twice. If you say "my address is 12 Lake Road" two times, the shop
> still has one address: 12 Lake Road. But if you say "take 12,400 rupees" two times, the shop
> takes the money two times.
>
> **Like in real life:** pressing the lift button again doesn't call two lifts. But putting
> money into a vending machine twice does buy you two drinks.

#### Advanced

> An operation is **idempotent** if doing it many times has the same **effect** on the server as
> doing it once. HTTP defines `GET`, `HEAD`, `OPTIONS`, `PUT` and `DELETE` as idempotent (RFC
> 9110 §9.2.2): `PUT` replaces a resource with the same body, `DELETE` removes it once. `POST`
> and `PATCH` are not: each `POST /payments` creates a new payment.
>
> Idempotent is about effect, not the response: a second `DELETE` may return `404`, a second
> `PUT` `200` instead of `201`, and both are still idempotent. Being idempotent is a promise the
> server keeps; the method name only says what is expected.
>
> **Example:** the same request twice.
>
> ```http
> PUT /orders/1042/address        → 200 OK   (address = 12 Lake Rd)
> PUT /orders/1042/address        → 200 OK   (address = 12 Lake Rd, unchanged)
>
> POST /payments                  → 201 Created  pay_81f2
> POST /payments                  → 201 Created  pay_9c04   (a second charge)
> ```

**Terms:** Idempotent · Idempotent methods · Safe methods

### Step 2. Where duplicates come from

**Scene:** three ways the same payment arrives twice, one after another, all without a key:

1. A double click: two packets leave Shopper A a moment apart.
2. A lost answer: the response travels halfway and vanishes (`lost`); Shopper A retries.
3. A timeout: Payments is slow, Shopper A gives up waiting and retries while the first request
   is still being handled.

The Payments DB badge counts up to "4 charges · 1 order".

#### Beginner

> The app didn't mean to pay four times. Once your finger tapped twice. Once the "done!" message
> got lost, so the app asked again. Once the helper was slow, so the app asked again before the
> first answer came. Each time, the helper thought it was a new payment.
>
> **Like in real life:** you post a letter, don't hear back, and post it again. The shop now has
> two letters and can't tell they are the same.

#### Advanced

> Networks deliver **at least once** when anyone retries: a client cannot tell "the request was
> lost" from "the answer was lost" from "the server is slow". Duplicates come from double
> submits, client retries after timeouts or resets, proxies and load balancers retrying,
> mobile apps resending after a network switch, and message queues redelivering. Exactly-once
> **delivery** is not possible over an unreliable network; an **exactly-once effect** is, if
> the receiver recognises repeats.
>
> Disabling the button after a click helps with one source only. The fix belongs on the server,
> because only it sees every attempt.
>
> **Example:** what the server sees.
>
> ```text
> 10:00:00.120  POST /payments  order 1042   ← click
> 10:00:00.310  POST /payments  order 1042   ← second click
> 10:00:05.400  POST /payments  order 1042   ← retry after a lost answer
> 10:00:15.900  POST /payments  order 1042   ← retry after a 10 s timeout
> ```

**Terms:** At-least-once delivery · Exactly-once effect · Double submit

## Chapter 2: Idempotency keys

### Step 3. One key per payment

**Scene:** Shopper A presses Pay. A badge appears on Shopper A: "key 7f3a… · saved". The payment
is sent with the key; the answer is lost (`lost`); Shopper A retries with the **same** key
("key 7f3a… · attempt 2"). Focus is on Shopper A.

#### Beginner

> Before paying, the app writes a secret number on the payment, like a ticket number: 7f3a. It
> keeps the number safe. If it has to ask again, it uses the **same** number. A new shopping
> trip gets a new number.
>
> **Like in real life:** a cloakroom ticket. You get one ticket for your coat, and you show the
> same ticket every time you ask about that coat.

#### Advanced

> The client generates the key **once per operation**, not per attempt: a random UUID v4
> (`crypto.randomUUID()`) is enough, and it must be unpredictable. It keeps the key with the
> operation (component state, a form library's submit state, or `sessionStorage` so a reload
> keeps it) and sends it on every retry in the `Idempotency-Key` header (IETF draft
> `draft-ietf-httpapi-idempotency-key-header`).
>
> It makes a **new** key when the operation changes (a different amount or cart) or after it
> has finished. Reusing a key for a new payment would make the server replay the old one.
>
> **Example:** the client side.
>
> ```ts
> const key = sessionStorage.getItem("pay:1042") ?? crypto.randomUUID();
> sessionStorage.setItem("pay:1042", key);
>
> await retry(() =>
>   fetch("/payments", {
>     method: "POST",
>     headers: { "Content-Type": "application/json", "Idempotency-Key": key },
>     body: JSON.stringify({ orderId: 1042, amount: "12400.00", currency: "LKR" }),
>   }),
> );
> sessionStorage.removeItem("pay:1042"); // done: the next payment gets a new key
> ```

**Terms:** Idempotency key · UUID

### Step 4. The server writes it down first

**Scene:** the payment reaches Payments. Payments writes to the Payments DB ("key 7f3a… · in
progress"), calls the Card processor (request and response; its badge: "charged once"), then
writes again ("key 7f3a… · done · 201 saved") and answers Shopper A ("paid").

#### Beginner

> The helper first writes the ticket number in its notebook: "7f3a: working on it". Then it
> takes the money. Then it writes down the answer next to the number: "7f3a: done, paid". Now
> it will remember this payment if anyone asks again.
>
> **Like in real life:** a cloakroom attendant writes your ticket number on the hanger before
> walking off with your coat.

#### Advanced

> The server keeps a table of keys: key, a fingerprint of the request, state (`in progress` or
> `done`), the stored response (status and body) and an expiry time. The first request:
>
> 1. **Inserts** the key as `in progress` with a unique constraint on the key. If the insert
>    fails, someone else has the key (steps 5–6).
> 2. Does the work: charges the card, creates the payment row.
> 3. Saves the response with the key and marks it `done`, in the **same transaction** as the
>    payment row, so there is never a payment without a saved answer or the other way round.
>
> The outside call (the Card processor) cannot be inside that transaction; the "Crash
> halfway" scenario and step 8 deal with that gap.
>
> **Example:** the key row.
>
> ```text
> key                                   fingerprint   state        response              expires
> 7f3a9c2e-4b1d-4e8a-9f60-2d5c1b8e3a47  sha256:c1e9…  done         201 {"id":"pay_81f2"} +24 h
> ```

**Terms:** Key table · Request fingerprint · Atomic transaction

### Step 5. A repeat gets the saved answer

**Scene:** the answer to the first request is lost (`lost`). Shopper A retries with the same
key. Payments looks the key up in the Payments DB, finds "done", and sends back the saved answer
without calling the Card processor. Badges: Payments "replayed"; Payments DB "1 charge · 2
requests"; Shopper A "paid".

#### Beginner

> The app didn't hear back, so it asks again with ticket 7f3a. The helper looks in the notebook:
> "7f3a: done, paid". So it just says "paid!" again. It doesn't take the money again.
>
> **Like in real life:** you show your cloakroom ticket twice; you still get one coat.

#### Advanced

> A repeat with a `done` key gets the **stored response**: the same status code and body as the
> first time, so the client can't tell a replay from the original. Stripe adds
> `Idempotent-Replayed: true` so clients and logs can tell. The server does not run the
> operation again and does not call anything downstream.
>
> Which responses to store is a choice: Stripe stores any result once the operation has started
> (including a `500`), so a retry gets the same failure rather than a second attempt with
> unknown effects. Validation errors that happen before anything changed are not stored.
>
> **Example:** the replay.
>
> ```http
> HTTP/1.1 201 Created
> Content-Type: application/json
> Idempotent-Replayed: true
>
> {"id":"pay_81f2","status":"succeeded"}
> ```

**Terms:** Replay · Stored response

## Chapter 3: The hard cases

### Step 6. Two at once

**Scene:** a double tap sends two requests with the same key a moment apart (`burst`). The first
marks the key "in progress" and calls the Card processor. The second finds the key "in progress"
and gets an error back at once: `409 Conflict` (badge on Shopper A: "409 · try again shortly").
The first finishes ("done"). Shopper A retries after a short wait and gets the replay ("paid").
Card processor badge: "charged once".

#### Beginner

> Two taps, same ticket, at almost the same moment. The helper is already working on 7f3a when
> the second one arrives. It says "I'm still doing that one, ask me again in a moment". When the
> app asks again, the answer is ready: "paid".
>
> **Like in real life:** you ask for your coat while the attendant is still walking back with
> it. They say "one moment", not "here's another coat".

#### Advanced

> Two requests with one key can arrive together, from a double submit or a client retrying
> before the first attempt has finished. Without care, both would see "no key yet" and both
> would charge. The unique constraint on the key makes the second insert fail; the server then
> answers `409 Conflict` (the IETF draft's choice, and Stripe's) and the client retries with
> backoff, as in the Retry module.
>
> The alternative is to make the second request wait for the first and then replay its answer.
> It is friendlier but ties up a connection and needs a timeout; `409` keeps the server simple.
>
> **Example:** the second request.
>
> ```http
> HTTP/1.1 409 Conflict
> Content-Type: application/json
> Retry-After: 1
>
> {"error":"idempotency_key_in_use","message":"A request with this key is still in progress."}
> ```

**Terms:** Concurrent requests · 409 Conflict · Lock

### Step 7. Same key, different request

**Scene:** Shopper A changes the cart, but the app (a bug) keeps the old key, and sends the same
key with a new amount (13,900). Payments compares the request's fingerprint with the stored one,
sees they differ, and refuses: `422`. Badges: Payments "different body"; Shopper A "422 · key
reused". Nothing is charged.

#### Beginner

> The app used ticket 7f3a again, but this time for a different, bigger payment. The helper
> notices that the ticket's notebook entry says 12,400 rupees, not 13,900. So it refuses:
> "that ticket was for something else".
>
> **Like in real life:** you hand in a ticket for a blue coat and ask for a red one.

#### Advanced

> The server stores a **fingerprint** of each key's request (a hash of method, path and body)
> and compares it on every repeat. A different request with a used key is a client bug: the
> IETF draft answers `422 Unprocessable Content`. Without the check, the server would replay
> the old payment's answer for a new payment, and the shopper would think the new amount was
> paid.
>
> On the client this is the rule from step 3: a new operation needs a new key. Tie the key to
> what is being paid (the cart's contents and amount), not only to the order number.
>
> **Example:**
>
> ```http
> HTTP/1.1 422 Unprocessable Content
> Content-Type: application/json
>
> {"error":"idempotency_key_reused","message":"This key was used with a different request."}
> ```

**Terms:** Request fingerprint · 422 Unprocessable Content

---

### Step 8. Expiry, and passing the key on

**Scene:** the payment again. Payments' call to the Card processor now carries **its own** key
(badge on the Card processor: "key pay_81f2 · charged once"). After the answer, the Payments DB
badge shows "key 7f3a… · expires in 24 h".

#### Beginner

> The helper's notebook can't keep every ticket forever, so it throws old ones away after a day.
> And when the helper asks the bank for the money, it also gives the bank a ticket number of its
> own. That way, if the helper has to ask the bank again, the bank won't take the money twice
> either.
>
> **Like in real life:** a parcel has a tracking number at every company that carries it.

#### Advanced

> **Expiry:** keys are deleted after a while (Stripe: at least 24 hours) to keep the table small.
> The time must be longer than any client will keep retrying; a retry after the key is gone is
> treated as a new payment (see "Key expired"). A unique constraint on the business key (one
> successful payment per order) is a good second safety net.
>
> **Passing it on:** each system can only protect itself. The Payments service makes the Card
> processor call idempotent too, by sending a key of its own that stays the same for this
> payment (for example the payment's id, `pay_81f2`). Then Payments can safely repeat that call
> after a timeout or a crash, and the whole chain charges once.
>
> **Example:** Payments calling the processor.
>
> ```http
> POST /v1/charges HTTP/1.1
> Host: api.cardprocessor.example
> Idempotency-Key: pay_81f2
>
> {"amount":1240000,"currency":"lkr","source":"tok_visa"}
> ```

**Terms:** Key expiry · Business key · End-to-end idempotency

## Scenarios

### Crash halfway (branches from step 4)

1. **The crash.** _Scene:_ Payments marks the key "in progress" and calls the Card processor,
   which charges ("charged once"). Before Payments can save the answer, it goes **down**. The
   answer to Shopper A never comes ("no answer").
   - _Beginner:_ The helper took the money from the bank, and then, before writing "done" in
     the notebook, it fell asleep. The notebook still says "7f3a: working on it". The app
     heard nothing.
   - _Advanced:_ The money moved, but the key row still says `in progress` and no payment row
     exists: the gap between an outside side effect and the local transaction. A plain retry
     would get `409` forever, and a careless server that started over would charge again.

     ```text
     key 7f3a…  in progress (since 10:00:00)   payment row: none   card: charged
     ```

2. **Recovering safely.** _Scene:_ Payments is back. Shopper A retries with the same key. The key
   has been "in progress" for over 60 seconds, so Payments takes it over and calls the Card
   processor again **with the same key** (`pay_81f2`). The processor recognises it and returns
   the earlier charge ("charged once · replayed"). Payments saves "done" and answers "paid".
   - _Beginner:_ The helper wakes up, sees "7f3a: working on it" from long ago, and asks the
     bank again with the same ticket. The bank says "I already did that one", so no money moves
     twice. Now the helper writes "done".
   - _Advanced:_ The key row records when it was locked; a lock older than a timeout (here
     60 s) is treated as abandoned and the next request with the key resumes the work.
     Resuming is safe only because the outside call carries its own key. Larger systems split
     the work into steps with saved recovery points and finish stuck keys in a background job.

     ```text
     10:01:10  retry, key 7f3a…   lock 70 s old → take over
     10:01:10  POST /v1/charges  Idempotency-Key: pay_81f2  → 200 (replayed, no new charge)
     10:01:10  key 7f3a… done, 201 saved
     ```

### Key expired (branches from step 8)

1. **A retry a day later.** _Scene:_ the first payment succeeded, but the answer was lost and the
   laptop went to sleep. 25 hours later the app wakes up and retries with key 7f3a. The key has
   expired; Payments treats it as new and charges again. Payments DB: "charged twice".
   - _Beginner:_ The app waited too long. The helper had already thrown the old ticket away,
     so it didn't know this was the same payment, and took the money again.
   - _Advanced:_ After expiry the key protects nothing. Clients must stop retrying well inside
     the key's lifetime (a deadline, as in the Retry module), and should ask before resending
     an old operation ("check the order's status first").

2. **The safety nets.** _Scene:_ the same late retry, but Payments first checks the order: a
   unique rule allows one successful payment per order, so it refuses ("already paid · order
   1042"). Shopper A shows "paid". Payments DB: "1 charge".
   - _Beginner:_ This time the helper also looks at the order number. Order 1042 is already
     paid, so it says so instead of taking the money again.
   - _Advanced:_ Combine the short-lived key with a lasting business rule: a unique constraint
     on `(order_id) WHERE status = 'succeeded'`, or the client checking `GET /orders/1042`
     before it resends after a long gap.

     ```http
     HTTP/1.1 409 Conflict

     {"error":"order_already_paid","paymentId":"pay_81f2"}
     ```

## Components

### Shopper A (client)

- **Purpose:** _Beginner:_ a person paying on the shop's web site. _Advanced:_ the client that
  owns the key: one per operation, kept across retries and reloads, replaced when the operation
  changes; it also disables double submits and retries `409` with backoff.
- **Talks to:** Payments.
- **Technologies:** `crypto.randomUUID()`, `sessionStorage`, TanStack Query mutations, form
  libraries' submit state.

### Payments (service)

- **Purpose:** _Beginner:_ the helper that takes the money and keeps the notebook. _Advanced:_
  the service that turns many attempts into one effect: records the key first, checks the
  fingerprint, replays stored answers, answers `409` for keys in progress and `422` for reused
  keys, and passes its own key downstream.
- **Talks to:** Shopper A, Payments DB, Card processor.
- **Technologies:** Stripe-style idempotency middleware, Postgres advisory or row locks.

### Payments DB (database)

- **Purpose:** _Beginner:_ the notebook. _Advanced:_ payments and the key table (key,
  fingerprint, state, locked at, stored response, expires at), with a unique constraint on the
  key, written in one transaction with the payment. Redis is a common alternative for the key
  table, at the cost of a second system and no shared transaction.

### Card processor (service)

- **Purpose:** _Beginner:_ the bank that actually moves the money. _Advanced:_ an outside API
  (Stripe, Adyen, a bank) that accepts its own `Idempotency-Key`, so its callers can repeat a
  charge safely.

## Review

1. **Illustrative numbers:** 24 h expiry, a 60 s abandoned-lock timeout, 12,400 LKR then 13,900
   LKR in step 7; time compressed on screen, real values on badges. _Recommended._
2. **Step 1 shows both `PUT` and `POST`.** One step, two short sequences with their own badges,
   so the contrast is in one picture. _Recommended._ The alternative is two steps (9 in all).
3. **Step 2 shows three sources of duplicates** (double click, lost answer, timeout) in one
   step, counting to "4 charges". _Recommended:_ it is the "why" for the rest of the module.
   Queue redelivery is mentioned in the text only, since there is no queue in this scene.
4. **Step 6's timing:** the two requests leave 0.1 s apart; the `409` is drawn as an error
   packet going back, and the shopper's retry after "1 s". _Recommended._
5. **The downstream key is the payment's id** (`pay_81f2`), not the client's key, so Payments
   owns its own key and never forwards a client's value. _Recommended._ The alternative is to
   forward a key derived from the client's (e.g. a hash of it).
6. **"Crash halfway" resumes after a 60 s lock timeout** on the next retry. _Recommended:_ it
   is the simplest correct recovery. Recovery points and background jobs are mentioned in the
   Advanced text only.
7. **"Key expired" has a second step with the business-key safety net**, answered with `409
order_already_paid`. _Recommended:_ a scenario that only shows the failure would end on a
   double charge with no fix.
